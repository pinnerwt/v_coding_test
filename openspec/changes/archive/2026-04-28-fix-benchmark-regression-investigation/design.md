## Context

`task2/scripts/trends.py` collects per-branch `results.json` files, computes `Run` summaries, and renders three SVG charts plus a `<!-- TRENDS:BEGIN -->` README block. The block currently contains only the SVG image refs and a latest-run table; there is no automated warning when the latest run's pass-rate drops materially.

Twenty-two benchmark runs have been recorded (2026-04-26 – 2026-04-28). Analysis shows:
- Overall pass-rate across the most-recent 8 runs: median 12 %, latest 0 %. The 12 pp gap exceeds the 5 pp threshold → a warning would have fired immediately.
- Two cases (`fixture-heading`, `fixture-count`) have clear regression-onset branches traceable to specific code changes.
- The remaining failures are either (a) cases that never passed (new live cases skipped in CI), (b) Qwen endpoint stochasticity on fixture cases, or (c) the case-count dilution when 4 new fixture cases were added.

The `regression_onset.py` script provides a git-bisectable record of the first-failing branch per case.

## Goals / Non-Goals

**Goals:**
- Add `flag_regression(runs: list[Run]) -> bool` to `trends.py` — pure function, no I/O, returns `True` when `latest.pass_rate < median(all pass rates) - 0.05`.
- Emit a `⚠️ Pass-rate regression detected …` line in the `<!-- TRENDS:BEGIN -->` block when the flag fires; this line appears immediately before the latest-run table.
- Add a deterministic test in `test_trends.py` covering the flag and the rendered warning.
- Add `task2/scripts/regression_onset.py` — standalone script that scans `benchmark/*/results.json` and writes `benchmark/_trends/regression_onset.md`.
- Check in the current `regression_onset.md` as a one-time artifact.

**Non-Goals:**
- Changing `score.py`, `benchmark.py`, or the eval runner.
- Email/Slack alerting — the README block is the only output surface.
- Per-case warning granularity inside the SVGs.
- Automated regeneration of `regression_onset.md` on every `trends.py` run (it's a separate script; regeneration is manual or CI-triggered).

## Decisions

### D1 — Threshold at 5 percentage points, not relative %

A relative threshold (e.g. "10 % worse than median") would produce noisy signals when the median itself is low (e.g. median=12 %, threshold=1.2 pp — too sensitive). An absolute 5 pp threshold is stable regardless of the median level and matches the ticket's "more than X" framing. The constant is named `REGRESSION_THRESHOLD_PP = 5` and lives in `trends.py` so tests can import it rather than hardcode `5`.

### D2 — Median over all runs, not a rolling window

The ticket says "running median". Using all recorded runs (not a rolling 5 or 10) means a historically high-performing repo will warn more readily if it drops. Given 22 runs with median 12 %, a rolling-5 window would actually be more lenient (recent median ~4 %); all-runs median is the more conservative and fairer signal. If run count grows large, a future ticket can cap the window.

### D3 — Warning injected as text in the README block, not in the SVGs

SVG mutation to add a warning badge requires significant SVG string surgery and is not testable without parsing SVG. Injecting a line in the existing Markdown block (between `<!-- TRENDS:BEGIN -->` and the latest-run table) is consistent with how `_render_readme_block` already works, stays testable as string assertions, and is human-readable in GitHub's README render.

### D4 — `regression_onset.py` as a separate script, not merged into `trends.py`

`regression_onset.py` is an investigative / reporting tool, not a real-time rendering path. Merging it into `trends.py` would bloat the always-run path and add git-log / git-blame I/O that is irrelevant in CI. A separate `uv run python -m scripts.regression_onset` invocation keeps responsibilities single-purpose.

### D5 — `regression_onset.md` is generated and checked in, not auto-regenerated by `trends.py`

The artifact's value is a point-in-time record with git SHAs, not a live dashboard. Regenerating it on each `trends.py` run would diff noisily in CI as the window shifts. Implementers regenerate it manually (or via a CI step in a future ticket) and commit the result.

## Risks / Trade-offs

- [Stochastic pass-rates] → The flag may fire on a run that happens to be a Qwen bad-luck run, not a code regression. Mitigation: the `⚠️` is advisory; the `regression_onset.md` provides a per-case history so readers can distinguish noise from signal.
- [Median computed over sparse history] → With only 22 runs the median is itself noisy. As runs accumulate the signal improves. No mitigation needed now.
- [regression_onset.md staleness] → If new benchmark runs are added without regenerating the file, the onset entries will be stale. The file header documents the generation command; a follow-up ticket can automate.

## Open Questions

1. Should `flag_regression` skip `--repeats > 1` aggregated runs when computing the median? Current answer: no — the `Run` dataclass already stores `pass_rate` post-aggregation, so all runs are comparable.
2. Should `regression_onset.py` attempt `git log` to identify candidate commits between onset branches? Decided: no — the branch names are already sufficient for `git bisect`; `git log` output is environment-dependent and would complicate the script and its tests.
